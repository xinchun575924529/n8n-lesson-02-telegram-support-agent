# docs/03-escalation.md

## 第三段 · 升级与防轰炸：危险信号来了，人怎么进来、又怎么不被烦死

### 结论先行

升级段的职责一句话：**该找人的时候立刻找人，不该找人的时候绝不多找一次**。愤怒 / 受挫 / 疑似安全问题 → 通知人工 + 语音安抚；但同一个用户在 30 分钟内反复发火 → 只收安抚（Holding），人工只被通知一次。实现这套"防骚扰"的，是一张 Google Sheets 锁表 + 一个时间窗口判断——**用最朴素的存储做最可靠的幂等**。

```
Parse Classification JSON（分类判决到手）
        │
        ▼
Get row(s) in sheet（读升级锁表：这个 chatId 最近升过级吗？）⚠️ 头号大坑在这
        │
        ▼
Evaluate Escalation Lock（Code：逐行比较 30 分钟窗口）
        │
        ▼
Already Escalated? ──是──▶ Holding Reply（安抚："专家已在处理"，结束）
        │ 否
        ▼
Escalation Check（if：angry / frustrated / security_risk=true 任一命中？）
        │ 是
        ▼
Set Escalation Lock（写锁：chatId + 当前时间戳）
        │
        ▼
Notify Human Agent（内部 bot 通知人工：SECURITY RISK 标记 + 转写原文）
        │
        ▼
Generate Voice Reply (TTS) → Send Voice Reply to User（语音安抚用户）
```

---

### 1. 升级判定：三个条件，各自独立

`Escalation Check` 是 OR 逻辑：

| 条件 | 例子 | 为什么升级 |
|---|---|---|
| `sentiment = angry` | "你们就是骗子！！" | 情绪失控，需要人 |
| `sentiment = frustrated` | "我已经等了三天了" | 接近失控 |
| `security_risk = true` | "我的私钥好像泄露了"（语气平静） | **看内容不看情绪**——安全事故必须人工 |

第三条件是最容易漏的：分类模型判定安全风险靠的是**触发词内容**（docs/02），哪怕用户礼貌地说"请问我的钱包被异常登录了怎么办"，也该升级。**情绪类升级管体验，安全类升级管底线。**

### 2. 30 分钟防轰炸锁：写锁 → 查锁 → 幂等

升级动作本身是一串重操作（写 Sheets + 通知人工 + 合成语音），如果用户狂发 10 条，绝不能执行 10 次。模板的解法：

1. **写锁（升级时）**：`Set Escalation Lock` 往锁表写一行 `chatId + escalatedAt(now)`；
2. **查锁（每次消息）**：任何消息在升级前都先 `Get row(s) in sheet` 读这个 chatId 的历史锁；
3. **判锁（Code）**：`Evaluate Escalation Lock` 逐行判断——存在 `escalatedAt` 距今 < 30 分钟 → 锁中。

锁中的消息走 `Already Escalated? → Holding Reply`：一句"我们的专家已经在处理，请稍候"，然后**整条流结束**——不通知人工、不写新锁、不再 TTS。

### 3. Evaluate Escalation Lock 的判锁矩阵（全可单测）

这个 Code 节点是我们 6 个断言覆盖的"行为规格"，也是你改锁逻辑时最好的参考：

| 输入情况 | 判定 | 语义 |
|---|---|---|
| 锁表为空（0 行） | 未锁 | 从未升级过，正常走升级判定 |
| 10 分钟前升过级 | **锁中** | 窗口内，拦 |
| 31 分钟前升过级 | 过期放行 | 窗口已过，允许再次升级 |
| `escalatedAt` 字段缺失 | 未锁 | 脏数据当无锁（宁可再升一次，不可漏升） |
| 多行混合，只要一行在窗口内 | **锁中** | 任何一条有效锁都算 |
| 锁中但 context 不同 | 仍锁中 | 锁按 chatId 粒度，不按内容 |

> 🧠 设计取舍：`escalatedAt` 缺失 → 放行，是"fail-open"（宁可重复打扰人工，不可漏掉真升级）；而安全类判定是"fail-closed"。两类失败模式要分清：**骚扰人工是成本问题，漏掉安全事件是事故问题**——成本问题放宽，事故问题收紧。

### 4. Notify Human Agent：人工收到什么？

内部 bot（第 2 个 Telegram bot，专门给人工收信，跟客服号分离）推送内容包含：
- **标记**：`⚠️ SECURITY RISK`（安全类）或情绪标记（angry/frustrated）；
- **转写原文**：用户到底说了什么（人工不需要重新去听语音）；
- **chatId**：方便人工在客服号里直接回复跟进。

客服号在用户侧发的是 **TTS 语音安抚**（Groq orpheus 合成："我们已收到您的消息，安全专家正在处理…"）——语音比文字更有"人在处理"的温度，这是模板的一个细节巧思。

### 5. ⚠️ 头号大坑：空表 = 整条升级链静默断掉（mock 实测踩中）

**现象**：mock 全链第一次跑 S1（安全风险升级）时，预期升级成功——实际**什么都没发生**，用户既没收到语音安抚，人工也没收到通知，而且没有任何报错。

**根因**：升级锁表是**空表**（客户刚上线，从没升级过任何人）。`Get row(s) in sheet` 查空表返回 **0 行数据**——而 n8n 的铁律是：**上游输出 0 项时，下游节点根本不会执行**（不是执行后得到空数组，是"没有输入就不跑"）。于是 `Evaluate Escalation Lock → Already Escalated? → …` 整条升级链被静默跳过，仿佛从地球上消失。

```
锁表（空）→ Get row(s) → 返回 0 行 ──▶ 下游全部不执行（静默！）
```

**修复**：锁表**永远预置一行占位数据**（或首次使用时初始化一行）。一行占位让查询永远有输出，判锁逻辑里再对"占位行/无关行"做正常过滤（它本来就要逐行比 chatId 和时间窗口）。

> 🧠 这是 n8n 里最阴的隐形杀手，没有之一：**HTTP 返回空数组你能看见，Sheets 查空表你连"空"都看不见——它表现为"下游没跑"**。凡是"先查后写"的模式（查锁、查重、查名单），都要问一句：**查不到时，下游还跑不跑？** 本课 S6（重复升级）和 S1（首次升级）两个场景专门覆盖了"有锁"与"空表"两种初始状态，就是为钉死这个坑。

---

## 坑点提示

- **升级顺序必须是"先查锁再升级"**：如果先升级再查锁，锁就失去意义了（每次都升级完才想起来查）。
- **时间比较用毫秒时间戳**：Sheets 存 `Date.now()`，判锁用 `now - escalatedAt < 30*60*1000`。别存人类可读字符串再 parse——格式一错全盘皆输。
- **锁表和日志表分开**：锁表只干"判幂等"一件事，行数少、查询快；别把锁混在 Interactions 大表里。

## 动手练习（详见 exercises 第 3 题）

1. 把锁窗口从 30 分钟改成 5 分钟，重跑"锁内重复升级"场景，验证 5 分钟内拦截、5 分钟后放行；
2. 在锁表里手工插一行"10 分钟前"和一行"31 分钟前"，跑一次消息，验证判锁矩阵的多行逻辑；
3. 复现头号大坑：把锁表清空，发一条安全风险消息，观察用户收不到任何回复——然后想想生产环境怎么加"空表守护"。
